## ⚠️ NEEDS EYES

- [ce:review / agent-native] **No revoke or list CLI for redemption codes.** When (not if) a code leaks on Reddit, the only kill switch today is hand-editing `redemptionCodes/{code}.active = false` in the Firestore console. One bad click resets `useCount`. Recommend two ~50-line scripts before going GA: `scripts/revoke-redemption-code.mjs` (sets `active:false`, optional `--expire <ISO>`) and `scripts/list-redemption-codes.mjs` (read-only inspect of codes + ledger entries).
- [ce:review / security] **No rate limiting on `/api/redeem-code`.** A signed-in attacker can enumerate codes at full Vercel concurrency. Random guessing is infeasible against the regex space, but predictable code names (`FRIEND-DAVE`, `LAUNCH-2026`) are dictionary-attackable and the differentiated `code_exhausted` vs `invalid_code` errors leak which patterns exist. Mitigation options: collapse the error taxonomy server-side, add per-uid attempt counter in Firestore, or require ≥8 random chars in the mint script's regex.
- [ce:review / security] **IDN / Punycode domain bypass in `normalizeEmail`.** NFKC lowercases but does not convert non-ASCII domains to ASCII punycode. A user could (theoretically) get two redemptions by registering both `user@пример.рф` and `user@xn--e1afmkfd.xn--p1ai`. Not exploitable through Google sign-in's standard flow (Google issues canonical ASCII), but worth closing — `import { domainToASCII } from 'node:url'` is one line.
- [ce:review / security] **`REDEMPTION_EMAIL_PEPPER` rotation has no migration path.** If the pepper is ever rotated (compromise, scheduled rotation), every existing ledger entry becomes unreachable and every prior redeemer gets a free second trial. Either add a `pepperVersion` field to the ledger doc, or document loudly in `api/lib/redemption.js` that this pepper must never be rotated without a re-hash migration script.
- [ce:review / architecture] **Schema drift between `redemption.js` and `revenuecat-webhook.js` is by convention, not by construction.** Both producers write `users/{uid}.subscription.*` with overlapping field shapes. Today's mitigation is "hope nobody forgets to update both files." Recommend extracting `api/lib/buildSubscriptionPatch({ source, plan, expiresAt })` shared by both writers before the next webhook schema change.
- [ce:review / patterns] **Three-place reason-code enum drift.** The strings `invalid_code`, `already_redeemed`, etc. are duplicated across `api/redeem-code.js` STATUS map, `src/lib/fetchWithRetry.js` REDEMPTION_REASONS Set, and `src/components/SettingsPage.jsx` REDEEM_COPY map. Adding a 7th reason will silently miss one. Either define once in `api/lib/redemption.js` and import on the server side, or add explicit "keep in sync" cross-reference comments in all three files.
- [ce:review / patterns + simplicity] **`fetchWithRetry` knows about a feature by name (`serviceName === 'Redeem'`).** The 400-branch peek is the first time this generic util has been gated on caller name. Cleaner: change the server to return 403 for `invalid_code`/`invalid_input` (they're auth-shaped rejects against a known code space) and reuse the existing unconditional 403 typed-error block. Removes a leaky cross-module dependency.
- [ce:review / agent-native] **Admin CLI has no environment confirmation.** `scripts/create-redemption-code.mjs` writes immediately if `GOOGLE_APPLICATION_CREDENTIALS` is set. A fat-fingered prod credential in dev silently mints a real code. Recommend printing `project_id` from the SA JSON and requiring typed confirmation before write.

## What got built

A redemption-code system with three independent abuse locks (per-uid, per-email, per-code-cap) wrapped in one Firestore transaction. Tal can mint single-use 1-year codes for friends and capped multi-use 1-week codes for the r/fellow Reddit drop. Users redeem inline from Settings → Subscription. Email canonicalization folds Gmail dots/plus-tags/googlemail.com so the same Google account can't drain two trials, and the email ledger uses peppered HMAC-SHA256 so a Firestore dump can't be rainbow-tabled. The grant writes into `users/{uid}.subscription.*` in the same shape the RC webhook uses, so existing entitlement checks (server-side `checkEntitlement.js` + client-side `SubscriptionContext`) pick it up with zero changes.

## Final /ce:review findings

Six review agents ran in parallel against the full feature diff. The headline outcome: the architecture is right (three-lock transaction + peppered HMAC + Firestore rules + Admin-SDK-only writes), but several review agents independently surfaced the same five issues that demanded fixes before the report was written. **All five fixes were applied in this run.** Items left in NEEDS EYES are legitimate concerns that need design decisions or follow-up work, not in-flight bugs.

### Fixed during this run (was-blocker, now-resolved)

⚠️ **(security + data-integrity) `normalizedEmail` plaintext in ledger doc defeated the HMAC pseudonymization.** `redemptionLedger/{hash}` was storing `normalizedEmail` right next to the hash, which made the entire EDPS/AEPD-cited HMAC design pointless — anyone with a Firestore dump could read every redeemer's email in cleartext. **Fixed:** dropped the field. Audit/refund workflows can join through `uid` → `users/{uid}.email`.

⚠️ **(data-integrity + architecture) Plan-downgrade silent corruption via `merge:true`.** The original write used `tx.set(userRef, {...}, {merge: true})`, which deep-merges the new `subscription` map into the old one. A user who previously redeemed a 1-year code and re-redeemed a 1-week code (allowed by the now-removed `lastEventType !== 'REDEMPTION_CODE'` carve-out) would silently overwrite `expiresAt` with a shorter date while orphaned RC fields like `cancelAtPeriodEnd: true` and `store: 'app_store'` survived. **Fixed:** switched to `mergeFields: ['redeemedCode','redeemedAt','subscription']` so the entire `subscription` map gets replaced wholesale; explicitly set `cancelAtPeriodEnd: false`; removed the `lastEventType !== 'REDEMPTION_CODE'` escape hatch (it was dead code due to the per-uid lock anyway).

⚠️ **(security + data-integrity) `c.durationDays` and `c.plan` not validated server-side at redeem time.** A bad backup restore or manual Firestore edit setting `durationDays: NaN` would write `subscription.expiresAt: null`, and the client's `!sub.expiresAt` defensive branch would then treat the grant as never-expiring. **Fixed:** added strict integer-range validation (`> 0 && <= 3650`) and string-non-empty plan check inside `runRedemption`.

⚠️ **(security) `codeExpiresAt` Date parse silently skipped expiry check on bad value.** `new Date(timestampObject) < new Date()` returns false on Invalid Date, so a Firestore Timestamp object (vs ISO string) would let an expired code through. **Fixed:** added NaN guard mirroring the pattern at `api/lib/checkEntitlement.js:79-86`.

⚠️ **(security + data-integrity) `tx.set(ledgerRef, ...)` could clobber an audit row if the pre-check ever broke.** **Fixed:** switched to `tx.create(ledgerRef, ...)`, which throws on existing doc. Belt-and-suspenders for the highest-value invariant in the system.

⚠️ **(security + patterns) Firestore rules relied only on default-deny for `redemptionCodes` and `redemptionLedger`.** Default-deny in `rules_version 2` is correct today, but a future catch-all rule added higher in the file would silently expose both collections. **Fixed:** added explicit `allow read, write: if false;` blocks for both collections, matching the precedent at `users/{userId}/secrets/{secretId}`.

### Verified safe (reviewers explicitly checked)

- Firestore rules block client writes to `users/{uid}.redeemedCode`, `redeemedAt`, and `subscription` on both create and update paths. `affectedKeys().hasAny([...])` correctly catches nested mutations including `subscription.freeUsage`.
- `email_verified === true` strict equality at `redeem-code.js:34`. Google sign-in always issues `email_verified=true`, so this is tight.
- Per-code transaction is correctly serialized by Firestore's automatic retry-on-contention. `c.useCount + 1` literal (vs `FieldValue.increment`) is correct because Firestore re-runs the callback with a fresh snapshot — matches the precedent at `api/lib/cors-auth.js:236-243`.
- Read-before-write contract honored. Three `tx.get` calls via `Promise.all` complete before any `tx.update`/`tx.set`.
- Subscription field shape matches what `SubscriptionContext.jsx:62-96` and `checkEntitlement.js:65-93` consume. Extra `grantedCode` field is ignored by consumers.
- `SubscriptionContext.jsx:67-72` defensive `expiresAt` check mirrors the server's expiry guard line-for-line.
- `fetchWithRetry.js` passes redemption reason codes through as typed errors without retry (`retries: 0` in `redeemCode.js:26`). Non-idempotent endpoint, non-retrying client. Correct.
- No hardcoded secrets, no SQL, no `dangerouslySetInnerHTML`, no XSS surface.
- Build passes (web bundle generated, no type errors, no syntax errors).

### Nitpicks not surfaced (per blockers.md)

- Three-place reason-code enum drift → moved to NEEDS EYES (real maintenance hazard).
- `RedeemError` class on the client is unused machinery vs the plain-`Error`-with-`.code` precedent → cleanup, deferred.
- `FRIENDLY_ERRORS` map in `fetchWithRetry.js` says "AI service" in 500/502/503 messages — a 500 from `/api/redeem-code` would surface as "The AI service hit an error" → cosmetic, deferred.
- `REDEMPTION_REASONS` vs `RedeemError` naming inconsistency → cosmetic.
- Near-exhaustion warning at 90% of `maxUses` is dead ops plumbing for a solo-COO project → could remove, but it costs nothing.
- `api/lib/redemption.js` could be inlined into `api/redeem-code.js` since it has one caller and no tests → architectural opinion, deferred.
