## What got built

Phase 0 of an onboarding rebuild that will replace the current single-page `OnboardingWizard.jsx` with a 13-screen conversion-optimized flow adapted from the Cal AI / Filtru / Finch framework. This phase handled the structural prerequisites only:

1. **Firestore rules** now allow `onboardingAnswers` and `onboardingCompletedAt` fields on `users/{uid}` profiles (previously blocked by a strict `hasOnly` allowlist), and declare an explicit immutable `users/{uid}/onboarding_events/{eventId}` subcollection for analytics (previously default-denied).
2. **`main.jsx` providers** (`SubscriptionProvider`, `PaywallProvider`) hoisted above Gate 5 so the future `OnboardingFlow` component can call `useSubscription()` and `usePaywall()` hooks during onboarding. Previously these providers mounted only at Gate 6, meaning onboarding was outside their scope — the original plan's Phase 4 was literally unbuildable without this fix.
3. **`SubscriptionContext`** now exposes a new `rcHydrated` flag that flips true on the first RevenueCat SDK response (success or failure) or immediately on web/non-native platforms. Consumers gating on subscription status during onboarding must wait for both `firestoreLoaded` AND `rcHydrated` before reading `hasPro` — spec'd to avoid a race where R13 reads stale hasPro before the RC listener has hydrated.

No user-visible change. The old `OnboardingWizard.jsx` still renders at Gate 5 exactly as it did before; the rebuild's new flow (Phases 1-5) is not yet wired up.

## Rip-it meta-lessons

- **Deepen-plan's review burst is the highest-value step in the pipeline for a feature this big.** It caught 3 critical blockers (provider scope, rules allowlist, subcollection rule) that the original plan would have hit in production. Worth the 7 parallel agent spawns every time for large features.
- **Single-atomic Firestore writes beat multi-step patterns in almost every case.** The original plan had a two-write `completeOnboarding` that two separate reviewers independently called out as solving a problem that doesn't exist. Single `setDoc(merge:true)` is atomic per document and cleaner.
- **For large features (5+ phases), triaging to ship a clean Phase 0 + full deepened plan is a legitimate rip-it outcome.** It lands real infrastructure (rules + provider scope) while preserving planning fidelity for continuation. Next run picks up with context already compressed into the plan.
